# 非常规招聘消息处理规则

这些规则用于本应用的 pi 活动 Agent，不写入或修改全局 pi 配置。可执行规则位于 `electron/core/activity-policy.ts`，每条消息都会注入系统提示词；图片补读与资源预算由读取器执行，不能只依赖模型自觉遵守。

示例使用合成单位、地点、链接和消息，不保存原群名、聊天库、个人标识或真实内推码。

## 两个独立判断

1. **是否有日程事实**：有明确场次，或有明确起止日期的跨日报名、招聘周期才提取；纯岗位、内推和网申推广不是日程。真实场次缺日期时可以进入“日期待确认”。
2. **来源是否完整**：缺图、截断、动态空页面、无法辨认都属于覆盖不足。有活动可以带警告入库；没有可确认活动也不能因此宣布已完整读完。

队列按 `reviewReasons` 判断是否为 `partial`，原始 `warnings` 全部保留在来源与任务诊断中。原消息或独立取得的正文充分支持活动、或严格符合纯岗位推广条件时，补充材料的警告不再等同于待检查。不完整 OCR 本身不能证明其未读部分是无关材料。仅链接/图片且内容未知、关键事实未确认、明确依赖其他来源时仍为 `partial`。旧提取器未提供 `reviewReasons` 时仍回退到原警告，避免错误清空问题。模型鉴权、网络等服务错误仍走失败重试，不伪装成无活动。非日程招聘信息现在单独保留在“招聘资讯”，尚未读全的原消息则放入其中的“待补全”列表，读取原因在详情中折叠保留。

## 分类规则

| 输入情况 | 处理 |
| --- | --- |
| 企业参加双选会，附今天、时间、地点、展位 | 提取企业参会活动，类型为双选会，展位写入描述；不补结束时间 |
| 校园招聘、职位专场、内推码、岗位投递入口，未注明场次或完整跨日报名周期 | 保留为资讯推送，不创建日程或“日期待确认”活动 |
| 群聊邀请或群二维码，能读到招聘相关群名 | 以“群聊：完整群名”为资讯标题，保留二维码图片；群名中的日期、二维码有效期都不单独生成日程 |
| 报名或招聘周期，明确写出跨日的开始和结束日期 | 按“其他”类提取一次，在“跨期事项”显示完整日期区间，不按天重复铺入日历 |
| 明确宣讲会，但网页图片无法全部辨认 | 保留正文已经支持的时间、地点等事实；不能用广告文字补缺字段 |
| 仅公众号链接，关键事实在海报中 | 先读图片；补读仍失败则待检查，不把“没有读到”当作“没有活动” |
| 正文夹杂历史推荐、公众号尾部群号、其他文章列表 | 不把这些旁支信息提取成当前通知的活动 |
| 网页只有动态应用外壳 | 保留原始链接和消息文字，记录无静态正文；不假称读到了浏览器渲染内容 |
| 模型给出无出处的报名链接 | 删除该字段，保留已确认活动和原来源；不猜路径、不把文章链接自动当报名链接 |
| 只有“扫码报名”或部分网址 | 留空报名链接；二维码需本机实际解码，印刷网址需原样识别 |
| 大量图片、长海报、多帧动图 | 在硬预算内分配覆盖范围，抽读必须保留警告，不声称完整读取 |
| 图片下载失败、QQ 附件过期 | 继续使用可读来源；已有 QQ 附件刷新路径可补救，无法恢复时待检查 |

## 招聘资讯与待补全

`submit_activities` 允许返回可选的 `information: { title, summary }`。无活动但有招聘公告、岗位/投递更新等可读资讯时提供来源支持的标题和摘要；无关聊天返回 null 或省略。已经提取活动时不重复生成资讯。未读材料不能由模型编造标题、摘要，也不能因为保留了资讯就撤销来源缺失状态。

新索引以原消息为单位保留资讯。完成且无活动时保存资讯推送；有实质读取缺失或最终失败时保存待补全，包括已有部分活动的消息，并提供关联活动入口。等待/运行中的补读仍显示在列表中。补读成功后重新归类：活动进入日程、非日程资讯进入推送、明确无关消息移除资讯入口。自动处理暂停时，“重新读取”只入队，不绕过暂停开关。

列表采用原消息发布时间，不将其当作活动日期；不受所选日历周约束，支持独立来源群筛选、标题/原文/文件名搜索和分页。每项保留原文、链接和文件名；没有标题时使用“公众号与网页推送”等通用名称。不会把转发自动标记为已验证的官方来源。

纯链接及通用标题优先使用真实公众号文章标题，分享卡片只能把同一个对象中的标题配给其链接。读取到网页标题后，即使后续模型失败也保留来源元数据；再次失败不覆盖已有标题。打开资讯列表时，通用公众号条目先从已有来源或卡片补标题，仍没有则后台只获取网页标题，最多并发 2 个、队列 40 项、单次 15 秒；成功/失败分别缓存 30/5 分钟。该流程无需开启模型处理，不下载图片、不调用模型、不清除原有来源缺失状态。身份、关注和消息版本在回填时重新校验，验证码、登录页与“微信公众平台”等通用页面名不能冒充文章标题。

首次升级只在本机恢复旧失败/待检查，以及无活动且原文可识别为招聘或公众号分享的已完成消息，不增加模型请求。仅有原链接且历史正文未保存时，不恢复或猜测摘要。读取记录按原样保留，页面不再重复铺开错误列表。资讯按账号、关注群与消息内容版本校验，编辑后旧条目立即不可见。

## 群聊二维码

图片 Agent 需要保留完整可读群名，合并视觉换行，例如“群聊：9月23日星河科技宣讲会-示例大学场”。这是图片邀请加入的群，不是转发图片的来源群；不以来源群名替换，不推定官方身份。标题不是笼统的“招聘图片与消息”或“海报”。

独立群二维码作为招聘资讯提交，不因群名包含“9月23日”或“宣讲会”就创建日程或日期待确认活动。摘要说明是群聊二维码；有效期只按图片原文注明，不视为活动日期、报名截止或跨期事项，不保证二维码当前仍有效。只有头像、图案无法转写或二维码未解码，不构成正文未读全；真正模糊的群名仍保留待补全原因，不补写未知文字。

若正文或显式引用另有独立场次通知，照常提取活动，并在描述中保留相关群名，不重复创建群二维码活动。进群地址不是默认报名链接；只有来源明确说明进群就是报名方式时才按报名证据使用，且不得猜测地址。普通社交群、关注公众号二维码不因此成为招聘资讯。

规则随图片识别和活动提取注入现有调用，不增加额外模型步骤，也不自动重跑全部历史图片。旧待补全图片在用户重新读取后应用新规则；本次不批量改写历史记录。

## 引用回复与拆分通知

- 显式引用以 `reply.data.id`（以及原始 CQ reply 标记）匹配同账号同群消息编号，不用群中最近一条消息代替。最多读取 4 条引用链；可另带前 30 条消息中引用同一原文的最多 2 条较早回复，形成不超过 6 条的关联来源。
- 原文不在归档中时，由已开启的处理任务经内部 QQ 接口补取；必须匹配原引用编号、群号、账号、合理的发送时间及群消息类型。此接口不对网页渲染端或模型开放。离线、取消关注、换号、错误响应不能带入其他来源。
- 当前回复与关联原文一起交给同一次提取，引用文件/海报同样可读取，所有来源共享页面、文件、图像和超时限制。来源时间随原文及图像标记送入模型，引用原文中的相对日期不能以回复日重解释。
- pi 规则要求把互补的时间、地点、附件联系起来；明确更正覆盖对应旧字段，简单致谢不重复提取原活动，无法判断的冲突保持未知。邻近但无明确关联的上下文不直接成为当前回复的活动。
- 引用缺失、编号重复、循环及截断产生可见的待补全原因。每次提交前核对引用内容版本，引用后到或变化会使相关回复重新排队；不因此重跑无关消息。新结构化来源中保留引用与相关回复快照，可在活动/资讯详情展开。

## 时间与链接

- “今天、明天、9.20”以**原消息的 Asia/Shanghai 时间**为基准，不以重试当天为准。合成消息发送于 `2026-09-20 09:00`、写着“今天14:00”，对应 `2026-09-20 14:00`。
- “2027届”是毕业届别，不表示活动发生于 2027 年。公众号编辑日期、工龄、培养周期不是活动时间。
- 已明确的历史活动仍使用其原日期，不顺延到未来。绝对日期和相对日期矛盾时，保留可靠事实，不强行猜日期。
- 来源网址校验保留查询参数和 `#/position/campus/` 等前端路由；只有发起 HTTP 下载时才去掉 fragment。
- 同一域名、同一路径但不同 fragment 不是相同报名证据。来源只给首页时不能猜一个岗位页面。
- 来源地址仍执行公开网络、凭据、端口和 DNS 校验，不为兼容动态页面放开内网访问或携带登录 Cookie。

## 跨期事项分栏

当前展示规则是 `type === '其他'`，且起止日期均已知、结束日期晚于开始日期。此规则直接作用于现有记录，不做数据库迁移，不改动来源，也不需要重新调用模型。

跨期事项独立列在周日历下方，每项只出现一次，优先显示较早结束的事项；所选周与日期区间相交才显示，并继续支持类型、来源群和搜索筛选。区间外的历史或未来周不显示该事项。跨年区间使用完整年份，不缩写造成歧义。

宣讲会、双选会、招聘会、面试、笔试即使跨天，也保留场次类型和日历展示；单日“其他”活动和日期未知通知不进入跨期栏。没有钟点本身不构成跨期事项的待核对原因，来源缺失、图片模糊等实际警告仍保留。日期区间已知但只有一个明确钟点时，只显示该钟点，不补午夜或结束时间。

模型提取同样区分上述两类：例如合成材料“某单位网上报名：2026年9月9日至10月15日”可提取一个跨期事项；仅有“10月15日截止”不能用消息发送日期、文章发表日期补出开始时间。

## 图片补读

1. 首次每批最多 6 个图像分片，只接受校验通过的 `submit_visual_text`，普通回答不能当作来源文字。
2. 没有结构化提交，或返回 `unreadable: true` 时，优先根据经过序号校验的 `unreadableImageIndices` 只补读失败位置；无法定位时分为每批最多 2 个分片，额外补读一轮。每条消息最多 6 次补读操作，达到上限仍继续后续批次的首次读取，不递归无限重试。每次 Agent 工具纠错最多 3 个回合，整条消息仍受 10 分钟上限约束。
3. 补读完整成功后撤销该批原来的模糊警告；仍有缺失则保留分片范围、可辨认事实，并继续处理后续批次。服务错误和取消不被吞掉。
4. 装饰、边框、普通标识、二维码图案本身无法转写，不等于招聘正文不可读；确实含糊的关键文字不得猜测。
5. 只有可完整读取的结果进入当前账号和模型配置隔离的有界缓存；整批补读恢复成功且合并文字不超限时缓存整批，避免重复通知再次补读。不缓存未提交和不可辨认结果。

## 图片预算

- 网页/消息图片来源上限由 48 调整到 96；仍最多 128 个分片、编码后 72 MB，不无限扩大模型输入。
- 为待处理的后续来源保留份额，避免第一段动图用光全部分片。长图或动图需要抽读时，在预算允许下覆盖首尾和中间内容。
- 动图受 240 帧、累计 8000 万像素预算限制；完整解码能容纳时一次解码，抽帧时分帧读取，避免把整段超限动图载入内存。
- 抽帧、跳过长图分片以及来源数超限都可能漏掉重要文字，必须保留读取记录；缺少独立充分证据时进入待检查。不能仅根据尺寸、帧数、扩展名就断言它是无关装饰。
- 该策略改善可用事实覆盖，不保证每篇长文章都能无警告处理；重要缺失仍需原图或人工核对。

## 多图网页 PDF

桌面提取默认将至少 8 张图片、或图片 URL 明确标示 GIF 的网页送入 PDF 路径。正文已独立支持完整日程时，仍先结束提取以避免无必要下载。少图网页与 QQ 独立图片保留原处理；没有图像能力时不生成需要图像读取的网页 PDF。少图网页中 URL 未标示的动图目前不能提前触发此路径。

打印器直接接收原始网址，使用隔离 Chromium 窗口加载原网页的 DOM、CSS 和脚本，再调用 `printToPDF`。已删除抽取正文、逐图解码/切片、重建 HTML 的旧生成器；采集器此前取得的 HTML 只用于判断是否需要 PDF，不作为替代网页交给打印器。自动滚动并激活 `data-src` / `data-original` 懒加载，等待图片和字体；保留网页自己的打印样式，不改变网格、图像、布局或选择动图首末帧。

临时窗口不接入应用桥梁、账号 Cookie 或模型密钥；网页资源 GET 经过公开地址校验和连接时 DNS 绑定的下载器，保留来源 CSP/CORS 限制。禁止非 GET、内网、弹窗、权限、文件下载、子框架、工作线程和 WebSocket，源码不能调用应用接口。资源重定向交还浏览器，以保持相对链接基址；每篇最多 768 次请求、128 MB 下载，最多并发 8 项，同主机最小调度间隔 30ms。原普通材料下载的 350ms 间隔不变。

PDF 只保留静态画面，作为 `notices` 在“静态转换说明”中折叠展示，不仅因此生成待补全警告。但原网页的横向滚动、超长裁切、未展开内容、缺图、关键文字不可辨认、页读取失败与超限仍为 `warnings`。成功打印和 PDF 所有页均处理，都不能证明原网页全部内容已经进入 PDF；尤其不能把未打印出来的投递信息断言为不存在。PDF 出错不会立即退回大量逐图读取。

生产桌面路径每批最多转图 4 页，先本机解码二维码，再交给图片 Agent 识别，等待该批处理后继续；不积累整篇图像，也不再受旧的 24 个图像页、7200 万累计转图像素或消息 128 个分片限制。活动 Agent 最后汇总全部已读批次，并保留真实页码、标题、原始来源链接和引用时间。规则要求读到后续批次再判断是否有投递信息，摘要优先保留招聘对象、岗位、地点、流程和投递入口；不把企业介绍当作完整招聘摘要。部分 OCR 仍不能证明其自身未读内容无关。

浏览器加载与打印限 120 秒，PDF 文件最多 24 MB；不再将网页图片按 96 张、长图 32 片或动图帧数转换为合成材料。页面滚动最长 45 秒、400 步，页面高度超过 30 万像素时保留覆盖不足记录；图片与字体分别最多等待 15 秒和 5 秒。后续 PDF 读取与模型调用使用整条消息的 10 分钟限时，不再套用原附件的 30 秒限时。PDF 安全上限为 256 页；每条消息的所有网页 PDF 批次及普通图片共用最多 6 次补读额度，取消会停止后续批次并销毁浏览器。

每篇 PDF 可提取正文最多 4 万字，超限后仍继续读取后续页面与链接。图片识别文字每篇最多 10 万字，按总页数为每批预留份额，超额批次截断时保留警告；含网页 PDF 的消息材料最终上限为 16 万字。文字或页数达到真实上限仍保留缺失记录，不以分批处理假称无限覆盖。兼容性调用未传入分批消费者时，仍有 24 个图像页与 7200 万像素限制；桌面实际提取已传入消费者。原 QQ PDF 附件的 5 MB / 20 页 / 8 个转图页 / 30 秒限制不变。

PDF 按账号独立保存，使用原始网址与打印结果的哈希标识，最多保留最近使用的 100 份或 256 MB。每次重新读取都加载原网页并重新打印，不能以 HTML 没变推断外部样式或动态内容未变，也不复用旧重排版 PDF。活动/资讯来源详情优先提供“网页 PDF”入口及“已处理 X / Y 页”；这个数字说明成功经过 PDF 页面处理，不代表原网页全部内容已打印、模型语义准确或所有动画帧已读取。超过 3 张的来源图片默认折叠为数量入口，保留旧图片证据，不再铺开几十个同名按钮。打开 PDF 前验证账号、关注群、消息版本和快照所属关系，不接受任意本机路径。清理后的快照会提示重新读取。新版只影响新处理或手动重试，旧摘要和处理页数在重新读取后更新，不自动重新处理全部历史网页。

## 验证与后续操作

## 高效处理与 PDF

- 原消息满足长度与场次条件时先进行一次提取，逐项核对日期、钟点、地点、来源引文。大学前缀只能来自原文或来源群名；模型组合引文按片段核对，不能为无出处的地点背书。核对失败则回到材料读取流程。
- 网页正文充分支持日程时跳过补充图片；“详见附件”“其他场次”“改期”等依赖或变更说明不会直接通过快速路径。来源链接始终保留。
- 纯岗位推广需为纯文字、足够长且没有活动、日期/截止或依赖说明，所带网址必须是岗位/投递入口；通过确定性检查才省略模型和网页请求。不能仅根据“校园招聘”四字归档未知内容。
- 普通 PDF 附件支持正文、精确链接和扫描/含图页转图。上限为 5 MB、20 页、8 个转图页、累计 2000 万输出像素、30 秒，转图仍进入全消息图片预算；网页 PDF 使用上节的分批路径。加密、损坏、超限会保留具体记录。字体和字符映射来自安装包，不访问 PDF 指定的外部资源。
- 新记录的材料读取记录在详情中默认折叠；真正需要用户行动的原因仍可见。前台检测到旧后台处理版本时提示重启，避免更新网页后误以为后台也已更新。
